CONTEXT
I'm building a Replay system for FTC Team Zenith 19084 (project
codename ChronoPath): a system that records robot telemetry (pose, gamepad
input) during autonomous/teleop runs on the Control Hub, then replays and
visualizes those runs in a separate Kotlin Multiplatform desktop/Android
app. The project has two subprojects: robot-module/ (Java, FTC SDK) and
replay-app/ (Kotlin Multiplatform, Compose UI).

We are starting Phase 0, Task 1 of docs/Plan.md: writing the binary file
format spec that every later task in every phase will reference as the
single source of truth. No code exists yet. This is a documentation-only
task.

GOAL
Create docs/replay-format-spec.md defining the complete binary format for
.autonomous and .teleop replay files — precise enough that two independent
implementations (Java on the robot, Kotlin in the app) will produce and
parse byte-identical output with zero ambiguity.

EXISTING ARCHITECTURE
Nothing implemented yet. Reference docs/AGENTS.md and docs/FTC_SYNTAX for
our coding conventions and FTC-specific constraints before writing this —
follow whatever conventions they establish for naming, units, and style.

TECHNICAL REQUIREMENTS
The spec document must contain, as separate clearly-labeled sections:

1. Magic bytes — a fixed byte sequence at file start identifying the
   format (and ideally a version byte/short for future-proofing).
2. Header field table — every header field, in order, with exact byte
   offset, size in bytes, type, and meaning (must include at minimum:
   magic, version, mode [autonomous/teleop], sample count, sample
   interval/dt info if fixed, and anything else needed to parse the file
   without external context).
3. Sample record field table — every per-sample field (X, Y, headingDeg,
   gamepad1 state, gamepad2 state, dtMs, and any channel-flagged optional
   fields), with exact byte offset within the record, size, type, and
   scale factor for any field stored as fixed-point/scaled integer rather
   than float. State explicitly whether values are little-endian or
   big-endian.
4. Channel bitmask table — bit positions and meanings for optional
   channels (start with a reserved bit for a future "turret angle"
   channel per Phase 7 of Plan.md), and how the header/record layout
   changes (or doesn't) when a channel is enabled.
5. File naming convention — confirm/document `Run<N>.autonomous` /
   `Run<N>.teleop`, and where `<N>` comes from (counter, timestamp, etc. —
   pick one and justify it).
6. Worked example — one fully hand-computed fake sample: state the
   engineering-unit input values, then show the exact resulting hex bytes
   for the full record (and the full header for one fake file), with each
   byte's value traced back to the table above it. This example will be
   copied verbatim into unit test fixtures in Phase 1 and Phase 3, so it
   must be exact and self-consistent.
7. I want the system to use raw floats for X/Y/heading in the record, with exactly 2 decimals rounded(for example 42.24 or 67.12)

CONSTRAINTS

- Do not write any code (.java, .kt, or otherwise) in this task.
- Do not invent fields/behavior not needed by Plan.md's later phases —
  check Phase 1–7 task descriptions and make sure the spec supports
  everything they reference (pose, gamepad1/gamepad2, dtMs, channel
  bitmask, mode) and nothing extra.
- Fixed-size records only — no variable-length fields — since Phase 1/3
  tasks assume a constant recordSize.
- Every numeric field must have an explicit byte width and, if not a raw
  float, an explicit scale factor and rounding rule.

ACCEPTANCE CRITERIA

- Every field referenced by any task in Plan.md Phases 1–3 has a home in
  one of the tables.
- The worked example's hex bytes are traceable field-by-field to the
  tables with no arithmetic left for the reader to verify.
