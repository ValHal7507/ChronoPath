TECHNICAL REQUIREMENTS
Before writing anything, re-read replay-format-spec.md §5, §5.1, §1.2,
and §1.4 in full — do not rely on memory from earlier in this project.

Add a method `public byte[] toBytes()` to ReplaySample that:

1. Allocates a 72-byte array (BASE_RECORD_SIZE from
   ReplayFormatConstants — reference the constant, do not hardcode 72).
2. Writes x, y, headingDeg at offsets 0x00/0x04/0x08 as little-endian
   float32, each having first gone through the exact §1.4 rounding
   algorithm (binary64 multiply by 100, floor(r+0.5), divide by 100
   restoring sign, then convert to float32) — implement the algorithm
   exactly as specified, not an approximation like Math.round().
3. Writes dtMs at offset 0x0C as little-endian uint32 (no rounding —
   integer as-is per §1.3).
4. Packs gamepad1's 15 booleans into a uint32 bitmask at offset 0x10
   using the BUTTON\_\* constants from ReplayFormatConstants (OR together
   the constants for every true field; unlisted/reserved bits stay 0),
   written little-endian.
5. Writes gamepad1's 6 axis floats at offsets 0x14–0x28, each through
   the same §1.4 rounding algorithm, little-endian.
6. Repeats steps 4–5 for gamepad2 at offsets 0x2C–0x44.
7. Returns the completed 72-byte array.

Use `java.nio.ByteBuffer.order(ByteOrder.LITTLE_ENDIAN)` (or equivalent
manual byte-shifting — your choice, since this is a code-structure
decision, not a spec question) to guarantee correct endianness; do not
rely on platform-default byte order anywhere.

Factor the §1.4 rounding algorithm into a small private helper method
(e.g. `private static float round2dp(float v)`) since it's applied to 8
different fields — do not duplicate the 4-step algorithm inline 8 times.
