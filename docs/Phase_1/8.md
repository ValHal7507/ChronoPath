GOAL
Write ReplayRecorder.saveToFile(String path) — flush the 16-byte header
plus every buffered sample record to a file on disk, exactly matching
docs/replay-format-spec.md's byte layout. Test this with a hardcoded
fake buffer, not a live robot — Control Hub storage isn't touched by
this task (that's Task 10's on-robot smoke test).

EXISTING ARCHITECTURE

- ReplayRecorder.java (robot-module/…/replay/) already has: a
  List<byte[]> records buffer, getSampleCount(), getRecords(),
  addSample(Pose, Gamepad, Gamepad, int) (translates SDK types →
  ReplaySample → toBytes(), appends), and writeHeader(int sampleCount,
  int mode) producing the exact 16-byte header — both already
  byte-verified against spec §8.1.
- docs/replay-format-spec.md §2 defines the overall file structure:
  16-byte header immediately followed by sampleCount × recordSize bytes
  of records, packed with no gaps, in recording order (record 0 first).
  §1.5 gives the exact size equation: fileSizeBytes ==
  HEADER_SIZE + sampleCount × recordSize == 16 + sampleCount × 72 for
  this project's channels=0 files. §4 offset 6 ties the header's mode
  byte to the file's extension (.autonomous / .teleop) — see §7 — but
  this task does not need to enforce that extension/mode agreement
  itself (naming is Task 9's OpMode-level concern per Plan.md; this task
  just writes bytes to whatever path string it's given).

TECHNICAL REQUIREMENTS
Before writing anything, re-read replay-format-spec.md §2 and §1.5 in
full.

Add `public void saveToFile(String path) throws IOException` to
ReplayRecorder that:

1. Determines mode from however addSample calls were made — but note
   ReplayRecorder currently has no stored "mode" field; writeHeader
   takes mode as a parameter, not stored state. Decide (and state your
   choice + reasoning): either (a) saveToFile(String path, int mode)
   takes mode explicitly as a parameter, matching writeHeader's own
   signature and keeping ReplayRecorder stateless about mode, or
   (b) ReplayRecorder gains a mode field set at construction or via a
   setter. Plan.md's task description says
   "flush header + buffer to a file" without specifying — this is a
   genuine design choice left to you per AGENTS.md's "use working
   judgment for pure structure decisions, state the choice."
2. Calls writeHeader(getSampleCount(), mode) to get the 16-byte header.
3. Writes the header bytes, then every record in records (in list/call
   order — record 0 first, per spec §2), to the file at path, with no
   gaps, no extra bytes, no trailing padding.
4. Uses standard java.io (FileOutputStream or similar) — no FTC-specific
   storage API needed for this task (Task 9's OpMode integration is
   where Control Hub file paths matter; this task just needs correct
   byte-for-byte disk writing given any path string).
5. Propagates IOException to the caller rather than swallowing it (per
   AGENTS.md: no silent failure).

CONSTRAINTS

- Do not call this from an OpMode or reference hardware — pure I/O

- Do not add channels/turret support.
- Do not modify writeHeader's or addSample's existing signatures/
  behavior — only add the new method (and, if you chose option (b)
  above, the minimal new field/setter it needs).
- Touch only ReplayRecorder.java.

ACCEPTANCE CRITERIA

- Given a ReplayRecorder with N buffered samples (built via addSample or
  directly via whatever your buffer design allows for a test), calling
  saveToFile(path, mode) produces a file of exactly
  16 + N × 72 bytes (spec §1.5), whose first 16 bytes equal
  writeHeader(N, mode)'s output and whose remaining bytes equal the N
  records concatenated in order.
- Works correctly for N = 0 in terms of byte layout (16-byte file) even
  though spec §4 says a real recorded file's sampleCount must be ≥ 1 —
  that ≥1 validation is a recorder-usage concern for Task 9, not
  something saveToFile itself needs to enforce, since Plan.md scopes
  this task as "flush header + buffer," not "validate before flushing."
  State whether you added such a check anyway and why/why not.
